## Scene intent

The residential acceptance finder must give a household visitor an immediate, factual answer about whether EVER accepts a selected item and what to do next, without requiring personal information or a quote request. It succeeds when visitors can search or browse operator-approved categories, select an item, understand its status through text and symbols as well as color, and reach verified preparation, fee, location, hours, and directions information using keyboard, screen reader, reduced-motion, or no-JavaScript paths.

## Composition

Use a predominantly white canvas with deep navy type. Blue sampled from the approved EVER asset is the single dominant accent because this scene is primarily about searching, selecting, and routing. Lime may appear only as a subordinate success indicator after contrast testing. Cyan may appear only in the short route transition. Neither color may replace a text status or symbol.

On desktop, use a 12-column grid. The heading and introductory copy occupy approximately five columns. The search form and category selector occupy approximately seven columns beside them. Place the result route directly beneath the selector, spanning approximately columns four through twelve so the selected item has a clear spatial path into its answer. Keep the result in one persistent location rather than creating a growing stack of cards.

Render categories as large controls in a two-column or three-column grid, depending on the approved category count and available width. Each control contains a recognizable name and one simple, consistent navy line illustration. Illustrations are decorative when the adjacent name supplies the same meaning. Avoid photography until authentic, approved equipment photography exists.

Use a section heading of approximately 48px to 72px on large screens, 34px to 44px on small screens, 18px to 20px introductory and result copy, and 16px to 18px control labels. Keep line lengths calm and operational. The result status should be visually stronger than its supporting details but smaller than the scene heading.

On mobile, stack the heading, support copy, search form, category controls, and result in that source order. Use two category columns only when every label remains readable and each target stays at least 48px high. Fall back to one column at narrow widths. Place the result immediately after the category list and never require horizontal scrolling, a pinned viewport, or a bottom sheet to read the answer.

The scene may follow the hero residential choice or lead the `/recycle` page. Its heading is an H1 when it is the page's primary content and an H2 when it follows an existing page H1. The selected hero route may terminate at this scene only if the approved page architecture supports that handoff.

## Motion

- Equipment choice response. Job: orient. Trigger: pointer hover or keyboard focus on a category choice. Duration: 150ms on entry and 120ms on exit. Easing: `ease-out` on entry and `ease-in` on exit. The boundary strengthens and the directional cue advances a few pixels. Reduced-motion fallback: apply the complete state immediately.
- Selection route and result resolve. Job: confirm and explain. Trigger: activation of an equipment choice after its verified result is available. Duration: 320ms. Easing: `cubic-bezier(0.22, 1, 0.36, 1)`. A representation of the selected label shifts no more than 12px toward the result, a short cyan line reveals from choice to outcome, and the correct check or information symbol settles beside the status. The same result container updates rather than stacking cards. Reduced-motion fallback: show the selected styling, complete route, symbol, and result on the first updated frame.
- Result replacement. Job: transition. Trigger: selection of a different item. Duration: 250ms within the same selection-response sequence. Easing: `ease-out`. Existing result details resolve into the new content in place. A new activation cancels unfinished movement and displays only the latest result. Reduced-motion fallback: replace the content immediately.
- Search filtering. Job: orient. Trigger: a submitted search or an enhanced input update. Duration: 0ms. Matching categories update without animated reordering so keyboard and visual positions do not drift unexpectedly. Reduced-motion fallback: identical behavior.
- Loading. No decorative or looping animation. Use static status text. If the chosen platform has a genuine progress indicator, it counts as the direct-input response and the route animation waits until loading completes.

Do not add a primary scroll animation or ambient effect to this scene. Do not animate the category illustrations, loop a scan effect, use parallax, smooth-scroll the visitor, or add a motion library. Plain CSS and a low-complexity SVG route are sufficient.

## Accessibility

Use a semantic section with one correctly ranked heading. Place the search controls in a form with a visible label. Use native search input, submit, links, lists, and headings before adding ARIA. Do not implement a custom combobox unless operator-approved data genuinely requires suggestions beyond the visible filterable category list.

Render published categories as a semantic list of real links or equivalent controls with valid no-JavaScript destinations. If links select a query-backed result, use `aria-current="true"` for the active item. Keep visual and source order identical. Decorative illustrations and route geometry use empty alternatives or `aria-hidden="true"` and contain no focusable SVG elements.

Focus order is heading content, search field, search submit, clear control when present, category choices in source order, result content, then any verified result action links. Do not move focus when filtering or replacing a result. When a selected result is returned through full-page navigation, preserve a meaningful document focus start and expose the selected item in the page title or primary result heading.

Enter submits the search form or activates a focused link. Space retains native behavior for any element implemented as a button. Do not reproduce native keyboard handling with generic containers. All functionality must remain available with keyboard input and without pointer hover.

Use a polite status region to announce the number of filtered categories after a user-initiated search. Announce a changed acceptance result once using the selected item and verified text status. Announce genuine loading and errors without moving focus. Do not announce decorative route movement, hover, or focus styling.

Communicate acceptance through the written status, a status-specific icon, border or shape treatment, and programmatic text. Do not rely on blue, cyan, lime, red, position, or animation. Errors require text and an information or warning symbol.

Meet WCAG 2.2 AA contrast: at least 4.5:1 for normal text, 3:1 for large text, and 3:1 against adjacent colors for focus indicators, control boundaries, status icons, and meaningful route strokes. Validate sampled production colors in their actual combinations. Each target must be at least 44 by 44 CSS pixels, with 48px to 56px preferred on mobile.

Support browser zoom to 200 percent and reflow at 320 CSS pixels without content loss, overlap, or horizontal scrolling. Search suggestions, if later approved, may not depend on placeholder text. The final category labels, status, and next steps must remain understandable with images and motion unavailable.
